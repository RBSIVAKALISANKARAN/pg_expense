PostgreSQL data model

How the database is connected

Detailed documentation of the tables, foreign keys, field types, constraints and the money-flow rules behind Expense OS.

Section 1

How each table connects

Account → Allocation

One account has spendable and savings allocation rows. Their balances add up to Account.total_balance.

Account → MoneyLocation

Each wallet points to one location such as rbsankaran_acc, Amma Cash, Appa Cash, Change Cash or Travel Card.

Account → Transaction

Every deposit, expense, allocation and wallet transfer belongs to the wallet whose balance changed.

Owner + Account + MoneyLocation + Allocation → MoneyPool

MoneyPool is the fine-grained reconciliation bucket: it answers who owns how much money, where it is, and whether it is spendable or savings.

Category → SubCategory → Item

The fixed expense hierarchy moves from broad category to optional subcategory to specific master item.

Transaction → Category / SubCategory / Item

Expense rows may reference the taxonomy, but these foreign keys are nullable so custom or uncategorized expenses remain possible.

Item → FoodProfile

Food items can have one profile describing food group, health classification and sugary status.

Transaction → FoodEvent → FoodEventItem

A food expense may have one FoodEvent and multiple FoodEventItem rows. Each entry can use a known Item or a free-text custom name.

Transaction → Transaction

related_tx links the outgoing and incoming sides of a wallet transfer so the two movements can be audited and reverted together.

SavedQuery / QueryExecutionLog

These tables support the SQL Playground without becoming part of the financial balance calculation.

Section 3

How money moves through the database

  1. Deposit: increases Account.total_balance, the selected Allocation.balance and the matching MoneyPool.current_amount.
  2. Expense: decreases those balances together and writes one Transaction ledger row.
  3. Transfer: decreases the source wallet and increases the destination wallet by exactly the same amount, creating paired transactions linked with related_tx.
  4. Reconciliation: Account.total_balance must equal the sum of allocations and the sum of money pools. A failed reconciliation aborts the database transaction.
  5. Taxonomy: Category → SubCategory → Item provides structure, while Transaction.variant remains free text for unpredictable details such as brands, providers and food variants.
